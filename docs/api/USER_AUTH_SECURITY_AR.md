# حماية التسجيل وتسجيل الدخول

## ما تم تطبيقه في هذا الفرع

- توحيد البريد الإلكتروني إلى أحرف صغيرة وإزالة المسافات قبل التسجيل وتسجيل الدخول.
- رفض نطاقات البريد المؤقت الشائعة في التسجيل، ورفض تسجيل الدخول بها حتى للحسابات القديمة.
- يمكن تحديث قائمة النطاقات عبر متغير البيئة `DISPOSABLE_EMAIL_DOMAINS`، وتُقبل أسماء النطاقات المفصولة بفواصل؛ كما تُحظر النطاقات الفرعية للنطاق المحظور.
- جعل تأكيد ملكية البريد شرطاً لتسجيل الدخول عبر الويب وواجهات الموبايل.
- اشتراط تأكيد الهاتف للحسابات الجديدة، مع الاحتفاظ بالحسابات الموجودة قبل الترحيل وفق سياسة انتقالية لا تفترض ملكية رقم الهاتف القديم.
- جعل رابط التأكيد موقّعاً ومحدود الصلاحية ويعمل دون جلسة مسجلة الدخول.
- عدم إصدار رمز Sanctum عند تسجيل حساب موبايل قبل التأكيد؛ يستجيب التسجيل بحالة HTTP 202.
- رفض الرموز القديمة للحسابات غير المؤكدة عند الوصول إلى API المحمي.
- إضافة إعادة إرسال عامة برسالة موحدة لا تكشف وجود الحساب.
- إضافة حدود للمحاولات على التسجيل وإعادة إرسال رابط التأكيد، مع الإبقاء على محدد محاولات تسجيل الدخول.
- رفع الحد الأدنى لكلمة مرور التسجيل عبر الويب إلى 8 خانات مع أحرف كبيرة وصغيرة وأرقام.

## أثر ذلك على الحسابات الحالية

تتضمن هذه التغييرات ترحيلين لقاعدة البيانات: إضافة `phone_verified_at` و`phone_verification_required` إلى `users`، وإنشاء جدول `phone_verifications` لتحديات OTP. القيمة الافتراضية لـ`phone_verification_required` هي `false` حتى لا يُطلب توثيق الهاتف بأثر رجعي من الحسابات الموجودة قبل الترحيل. كل مسارات إنشاء الحسابات الجديدة تفعّل هذا الشرط؛ لذلك يلزم توثيق البريد والهاتف قبل تسجيل الدخول. عند تغيير رقم الهاتف يُعاد ضبط توثيقه ويصبح الشرط إلزامياً لذلك الحساب. يظل البريد الموثق شرطاً للجميع، وتظل قائمة البريد المؤقت مطبقة على الجميع.

## إعدادات النشر المطلوبة

1. اضبط `APP_URL` على عنوان HTTPS الفعلي، وتحقق من إعدادات الوكيل العكسي إذا كان التطبيق خلف proxy.
2. اضبط SMTP إنتاجياً واختبر وصول رسالة التأكيد فعلياً. لا تستخدم `MAIL_MAILER=log` في الإنتاج؛ هذا يسجل الرسائل ولا يرسلها للمستخدم.
3. احتفظ بقائمة النطاقات في `DISPOSABLE_EMAIL_DOMAINS` محدثة. بعد تعديلها في بيئة تستخدم config cache، أعد بناء/مسح ذاكرة الإعدادات بالطريقة المعتمدة في النشر.
4. اختبر التسجيل والتأكيد والدخول وإعادة الإرسال على بيئة staging قبل تطبيق التغيير على الإنتاج.

## ما لا تضمنه هذه الحماية

قائمة النطاقات تحظر مزودي بريد مؤقت معروفين فقط، ولا يمكنها اكتشاف كل نطاق جديد. تأكيد البريد يثبت إمكانية الوصول إلى صندوق البريد، لكنه لا يثبت الهوية القانونية ولا يمنع شخصاً محتالاً من استخدام بريد دائم يملكه.

قبل فتح التسجيل العام على نطاق واسع، اختبر تكامل Twilio ووصول OTP فعلياً على staging قبل الإنتاج، مع التحقق من صحة بيانات الاعتماد وحدود الإرسال والبلدان المسموح بها. أضف CAPTCHA مثل Cloudflare Turnstile بعد إعداد مفاتيح الخادم، وفحصاً محدثاً لنطاقات البريد المؤقت أو مزود تحقق بريد، ومراقبة محاولات الدخول والتسجيل، وMFA إلزامياً للمشرفين، ومراجعة صلاحيات الوصول وسجلات النشاط. طبّق أيضاً حماية WAF/edge ضد DDoS والطلبات الآلية، واختبر النسخ الاحتياطية واستعادة البيانات.

## الاختبارات

أضيفت اختبارات لتسجيل الويب دون إنشاء جلسة، ورفض الحسابات غير المؤكدة، واستخدام رابط التأكيد كضيف، ورفض النطاق المؤقت في الويب والموبايل، وعدم إصدار رموز موبايل قبل التأكيد، ورفض الرموز القديمة للحسابات غير المؤكدة.

يجب تشغيل مجموعة Laravel كاملة في CI قبل الدمج؛ لا يُعد فتح طلب الدمج أو إنشاء الالتزامات بديلاً عن نجاح الاختبارات.
